Why bqkit

Skip the REST pagination, stream the rows.

Reading a large query result through the BigQuery REST API is slow. The Storage Read API streams rows in Avro or Arrow over gRPC instead. bqkit wires that path into Spring Boot.

Avro or Arrow

Run a query into a destination table, then stream it through BigQueryReadClient: rows in Avro, or columnar batches in Arrow.

Impersonation

Application Default Credentials, with optional service account impersonation.

Emulator tests

A @ServiceConnection for the BigQuery emulator with Testcontainers: no GCP project needed.

Backs off

Every bean steps aside when your application defines its own.

The read path

One call, three steps.

One call to query(sql, destination) runs a query job, lands the result in a table, then streams that table in Avro (QueryAvroReader) or in Arrow (QueryArrowReader).

Modules

Take only what you need.

Use the core alone, or let the starter wire it for you.

Avro or Arrow

The starter declares both readers: inject the one that fits the use case. QueryAvroReader reads row by row: it returns the rows as a List<GenericRecord>, which holds the whole result in memory, or hands each row to a callback, for large results. QueryArrowReader hands the result to a callback, one columnar record batch at a time: to work on columns.

QueryAvroReader streams the rows with query(sql, rows), query(sql, destination, rows) or readTable(table, rows):

java — stream Avro rows 
reader.query("SELECT name FROM `my-project.shop.products`", TableId.of("shop", "query_result"),
        row -> System.out.println(row.get("name")));

The next response of the stream is only requested once every row of the current one has gone through the callback, so a slow callback slows the read down instead of filling the memory. If a row cannot be decoded or the callback throws, the read stops and the stream is cancelled: the rows before it have already been handed to the callback.

QueryArrowReader takes the same arguments, and calls the callback once per record batch:

java — stream Arrow batches 
reader.query("SELECT name, price FROM `my-project.shop.products`", TableId.of("shop", "query_result"), batch -> {
    VarCharVector name = (VarCharVector) batch.getVector("name");
    for (int i = 0; i < batch.getRowCount(); i++) {
        System.out.println(name.getObject(i));
    }
});

The batch is released once the callback returns: copy what you keep. Arrow needs access to java.nio on Java 21: start the application, and the tests, with --add-opens=java.base/java.nio=ALL-UNNAMED. Without it, the first read fails with Failed to initialize MemoryUtil.

Every bean backs off when the application defines its own. Defining a BigQueryConnectionDetails bean replaces the connection built from the properties.

The starter ships the configuration metadata of the bqkit.* keys: your IDE completes and documents them in application.yml.

Without the starter

bqkit-core has no Spring dependency. Declare the beans yourself, with keys of your own in application.yml:

pom.xml — core only 
<dependency>
    <groupId>io.github.bqkit</groupId>
    <artifactId>bqkit-core</artifactId>
    <version>${bqkit.version}</version>
</dependency>
application.yml — your own keys 
bigquery:
  project-id: my-project
  impersonate-service-account: reader@my-project.iam.gserviceaccount.com # optional
java — BigQueryConfig 
@Configuration
public class BigQueryConfig {

    @Bean
    BigQueryConnection bigQueryConnection(
            @Value("${bigquery.project-id}") String projectId,
            @Value("${bigquery.impersonate-service-account:}") String impersonateServiceAccount) {
        return BigQueryConnection.google(projectId, CredentialsFactory.create(impersonateServiceAccount));
    }

    @Bean
    BigQuery bigQuery(BigQueryConnection connection) {
        return BigQueryClients.bigQuery(connection);
    }

    @Bean(destroyMethod = "close")
    BigQueryReadClient bigQueryReadClient(BigQueryConnection connection) {
        return BigQueryClients.readClient(connection);
    }

    @Bean
    QueryAvroReader queryAvroReader(BigQuery bigQuery, BigQueryReadClient readClient) {
        return new QueryAvroReader(bigQuery, readClient);
    }
}

BigQueryConnection.google(...) targets the Google endpoints; BigQueryConnection.emulator(...) targets an emulator. The @ServiceConnection of bqkit-test relies on the starter.

Credentials

Read with a service account's permissions.

Set impersonate-service-account to read with a service account's permissions instead of your own.

Testing

Declare the emulator, Spring Boot does the rest.

Declare the emulator container: Spring Boot connects every bqkit bean to it.

pom.xml — test dependency 
<dependency>
    <groupId>io.github.bqkit</groupId>
    <artifactId>bqkit-test</artifactId>
    <version>${bqkit.version}</version>
    <scope>test</scope>
</dependency>
java — emulator container 
@SpringBootTest
@Testcontainers
class ProductRepositoryTest {

    @Container
    @ServiceConnection
    static final BqkitBigQueryEmulatorContainer EMULATOR =
            new BqkitBigQueryEmulatorContainer();
}

BqkitBigQueryEmulatorContainer runs ghcr.io/goccy/bigquery-emulator:0.8.1 on project testproject and exposes the gRPC port of the Storage Read API.

A complete test

The application code queries through QueryAvroReader:

java — ProductRepository 
@Repository
public class ProductRepository {

    private static final TableId RESULT = TableId.of("shop", "products_in_stock");

    private final QueryAvroReader reader;

    public ProductRepository(QueryAvroReader reader) {
        this.reader = reader;
    }

    public List<String> findNamesInStock() {
        return reader.query("SELECT name FROM shop.products WHERE stock > 0", RESULT).stream()
                .map(row -> row.get("name").toString())
                .toList();
    }
}

The test seeds the emulator with the BigQuery bean, calls the repository, then checks the result:

java — ProductRepositoryTest 
@SpringBootTest
@Testcontainers
class ProductRepositoryTest {

    @Container
    @ServiceConnection
    static final BqkitBigQueryEmulatorContainer EMULATOR =
            new BqkitBigQueryEmulatorContainer();

    private static final TableId PRODUCTS = TableId.of("shop", "products");

    @Autowired
    BigQuery bigQuery;

    @Autowired
    ProductRepository repository;

    @Test
    void finds_the_names_of_the_products_in_stock() {
        // Given
        bigQuery.create(DatasetInfo.of(PRODUCTS.getDataset()));
        bigQuery.create(TableInfo.of(PRODUCTS, StandardTableDefinition.of(Schema.of(
                Field.of("name", StandardSQLTypeName.STRING),
                Field.of("stock", StandardSQLTypeName.INT64)))));
        bigQuery.insertAll(InsertAllRequest.newBuilder(PRODUCTS)
                .addRow(Map.of("name", "banana", "stock", 3))
                .addRow(Map.of("name", "apple", "stock", 0))
                .addRow(Map.of("name", "cherry", "stock", 12))
                .build());

        // When
        List<String> names = repository.findNamesInStock();

        // Then
        assertThat(names).containsExactlyInAnyOrder("banana", "cherry");
    }
}

The emulator keeps its data for the lifetime of the container: with several tests in a class, give each its own dataset or destination table (see Emulator limits).

Emulator limits

The emulator is not BigQuery.

Keep these in mind when a test behaves differently from production.

avro

Hyphenated project ids break Avro reads. The emulator builds the Avro namespace from the project id, so test-project (the Testcontainers default) fails. testcontainers-java#12123 proposes withProjectId.

bqkit uses testproject.

query(sql)

query(sql) fails in Avro. The emulator names the anonymous result table after the job id, which is not a valid Avro name (bigquery-emulator#527). QueryArrowReader is not affected.

Use query(sql, destination) in tests.

truncate

WRITE_TRUNCATE is ignored. query(sql, destination) appends to the destination table instead of replacing it, so a second query into the same table returns the rows of both.

Use a distinct destination table per test, or drop it before each test.

See also bigquery-emulator#508.

prodNone of these limits affect BigQuery itself.
